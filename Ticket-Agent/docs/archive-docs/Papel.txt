1. CONTEXTO DA DECISÃO HUMANA (FATO CONSUMADO)

Após validação operacional real, a intenção CREATE_USER foi redefinida para refletir o processo efetivo da organização.

A versão anterior estava excessivamente rígida e exigia informações que:

o solicitante não possui no momento do pedido;

não são necessárias para abertura válida do ticket;

são tratadas posteriormente pelo N2/N3.

A nova governança prioriza identidade, vínculo e rastreabilidade, não definição de acesso.

2. ATUALIZAÇÕES OBRIGATÓRIAS — DOCUMENTO MESTRE DE DECISÃO (DMD)

Atualizar o DMD para versão 1.4 com as seguintes alterações obrigatórias:

2.1. Redefinição da Intenção CREATE_USER

Nova definição oficial:

CREATE_USER refere-se exclusivamente à criação de identidade digital básica
(usuário de rede, sistemas internos ou VPN).
Não inclui definição de perfil de acesso, permissões detalhadas, reativação ou alteração de acessos.

2.2. Subtipos Lógicos de CREATE_USER (Novo)

Adicionar seção explícita:

CREATE_USER possui subtipos condicionais:

Usuário Efetivo / Nomeado

Estagiário

Terceiro (se aplicável ao ambiente)

O subtipo altera os campos obrigatórios.

2.3. Campos Obrigatórios (Hard Requirement — Atualizado)

Substituir a lista anterior pela seguinte:

Campos SEMPRE obrigatórios

tipo_usuario (efetivo | estagiário | terceiro)

nome_completo

departamento / lotação

Identificador Principal (condicional)

Usuário efetivo: matricula_id

Estagiário: rg

Terceiro: identificador conforme política local (se existir)

CPF

Obrigatório apenas para usuários não estagiários

2.4. Campos REMOVIDOS como obrigatórios

Remover explicitamente como hard requirement:

nível de acesso

data de início

data de fim

aprovador explícito

Justificativa:

Esses dados são definidos após a abertura do ticket ou fora do chat
e não devem bloquear o fluxo de triagem.

2.5. Datas Vagas — Reclassificação

Atualizar política:

Data de início não é obrigatória

Se o usuário informar datas vagas:

aplicar regras já definidas (“semana que vem”, “urgente”, etc.)

gerar alerta de confirmação

Se não informar:

o ticket segue normalmente

3. ATUALIZAÇÕES — POLÍTICAS OPERACIONAIS

Atualizar para refletir a nova governança:

CREATE_USER — Política Operacional Revisada

O agente NÃO deve solicitar:

nível de acesso

perfil de sistema

permissões detalhadas

O agente DEVE:

identificar o tipo de usuário

coletar identidade mínima conforme subtipo

aceitar pedidos feitos por terceiros (RH ou chefia imediata)

Adicionar observação:

CREATE_USER não é autoatendimento do usuário final na maioria dos casos.

4. AJUSTE DE TERMINOLOGIA (Correção Importante)

Onde constar referência a N3 para criação de usuários, corrigir para:

N2, conforme operação real.

5. CONGELAMENTO DA INTENÇÃO

Após aplicar as alterações acima:

Marcar CREATE_USER como CONGELADA

Nenhuma nova regra, exceção ou campo deve ser sugerido sem nova deliberação humana formal
