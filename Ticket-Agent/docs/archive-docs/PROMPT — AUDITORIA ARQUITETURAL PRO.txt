Método Obrigatório de Análise

Para CADA pasta e CADA script, execute o seguinte processo:

1. Identificação

Qual é a responsabilidade declarada desse arquivo?

Ele atua em:

memória?

fluxo?

extração?

validação?

decisão?

2. Avaliação Arquitetural

Avalie se o código:

Depende excessivamente de histórico textual

Usa lógica probabilística onde deveria ser determinística

Mistura NLU, NLG e Flow Logic

Confia no LLM para “decidir” estados

Usa validação sintática onde deveria ser semântica

Assume que “conversar resolve”

3. Confronto com Boas Práticas

Confronte explicitamente com os conceitos já estudados:

Isso viola State-Driven?

Isso ignora State Store?

Isso reforça Chat-Driven?

Isso cria risco de looping?

Isso cria risco de amnésia?

Isso contradiz padrões de LangGraph / Rasa / agentes transacionais?

4. Classificação do Problema

Classifique cada achado como:

Anti-pattern arquitetural

Definição obsoleta

Risco de inconsistência futura

Fonte potencial de looping

Fonte potencial de perda de contexto

Acoplamento indevido

5. Documentação (Sem Solução)

Para cada ponto identificado, documente:

Arquivo / Pasta

Trecho ou lógica envolvida (descrição, não patch)

Qual regra ou boa prática moderna é violada

Por que isso conflita com o que já foi validado

Quais sintomas isso explica nos testes (ex: looping, esquecimento)

⚠️ Não propor correção. Não sugerir código.

Exemplo de Profundidade Esperada (Ilustrativo)

Arquivo: nodes/viability_node.py
Problema: Lógica delega ao LLM a decisão de “viável ou não”, baseada em linguagem natural.
Violação: Flow Logic probabilística em vez de determinística.
Conflito: Arquitetura State-Driven exige regras explícitas baseadas em estado.
Risco: Loop infinito de perguntas mesmo com dados completos.
Sintoma observado: Falha em atingir READY nos cenários 01, 05 e 07.
