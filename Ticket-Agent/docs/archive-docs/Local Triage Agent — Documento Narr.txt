Objetivo: Documentar, com suas palavras e contexto real, todas as regras, observações, fluxos e decisões que você trouxe ao longo do desenvolvimento do agente, em uma narrativa única e estruturada.

🧠 1. Contexto Operacional Real

Nós trabalhamos em um ambiente institucional (servidores públicos, suporte de TI) onde os usuários são leigos tecnicamente. Eles descrevem problemas de forma natural — muitas vezes informal — como:

“A impressora do RH não está funcionando”

“Esqueci minha senha”

“Preciso de 3 fones porque os que tínhamos estão estragados”

Esses usuários não estão acostumados com termos técnicos como IP, DNS, caminhos de fila ou patrimônio. Então o agente não pode perguntar por esses campos. Isso foi uma regra firme desde o início:

O agente nunca deve usar jargão técnico nem exigir procedimentos físicos (ex: “olha o cabo”, “verifique o IP”).

Você repetiu isso muitas vezes com exemplos reais, e isso moldou todas as regras de como o agente deve interagir.

🧾 2. Premissas Importantes
Usuário Leigo

O agente sempre assume que o usuário é não técnico, por isso:

Jamais pede IP

Não exige que o usuário verifique hardware fisicamente

Usa linguagem acessível

Aceita referências informais de ativos (“aquilo da sala do RH”)

Enriquecimento Automático

Você explicou que dados técnicos como IP, patrimônio, serial, hostname, etc., são coletados por automações externas e cruzados com inventário quando possível.
Isso não é função do chat, então o agente não pergunta esses campos quando faltam.

Exemplo real que você mencionou:

“Não existe impressora pessoal! As impressoras são fornecidas e mantidas pela Simpress/HP para uso coletivo.”

Essa percepção definiu que o agente deve aceitar referências informais para impressoras — “a impressora daqui”, “a Kyocera grande” — sem pedir IP, patrimônio ou detalhes técnicos.

🚦 3. Intenções e Fronteiras (com seu contexto)

Você trouxe uma classificação prática de intenções que mapeia intuitivamente o que os usuários tentam fazer:

RESET_PASSWORD

Problemas de acesso/login

Assume Rede/Windows por padrão quando o usuário diz “esqueci minha senha”

Este caso é muito comum, por isso a regra foi reforçada para que o agente seja direto e claro, sem perguntar campos que o usuário não tem — apenas assume e coleta identificador de usuário quando necessário.

CREATE_USER

Este foi um dos pontos mais discutidos:

Você explicou que:

A criação de usuários normalmente é solicitada pelo RH ou por um gestor, não pelo próprio usuário

Para usuários de rede (servidores efetivos), os pedidos vem do RH

Para estagiários, o identificador correto é o RG, não CPF

Para terceirizados, pode ser matrícula ou nome da empresa

Campos como nível de acesso, cargo, data de término não devem ser coletados no L1

Data de início não é bloqueante — se útil, inferida automaticamente, mas não deve bloquear o ticket

Você também salientou que dados como sistema ou permissões específicas não são de responsabilidade do agente L1 — isso é feito em camadas superiores (N2/N3).

EQUIPMENT_REQUEST

Aqui você trouxe muito contexto real:

Equipamentos pessoais não são suportados

Os equipamentos de uso institucional (desktop/notebook/monitor/mouse/teclado) são atendidos

Headsets/smartphones/fones simples do usuário não entram

A regra entre Incidente × Requisição é essencial

Incidente: equipamento parou de funcionar de repente

Requisição: novo pedido ou troca por desgaste (“meu mouse está velho”)

Você também disse:

“Quantidade quando for requisição: sim, podemos aceitar número livre, sem validação e sem limite.”

Isso mostra que o agente não deve questionar quantidade ou pedir aprovações no L1 — isso não é função dele.

Essa distinção foi crítica para que o agente:

Não perguntasse “é incidente ou requisição?” explicitamente

Inferisse automaticamente, ou assumisse default (incident se descrito problema)

PRINTER_ISSUE

Outro caso bem pragmaticamente descrito:

Você reforçou que:

Eles só têm impressoras de uso coletivo

Não há impressoras pessoais

O agente não deve fazer perguntas técnicas

Identificadores informais são suficientes

Exemplos que você deu, e que guiaram a regra:

“A impressora do corredor”, “Aquela grande perto da porta”, “A do RH não está imprimindo”

O bom funcionamento disso foi essencial porque usuários simplesmente não sabem modelo, IP ou patrimônio.

VPN_ACCESS

Você foi claro:

O agente não cria credenciais VPN

Ele apenas concede o acesso ou ajuda com instalação

Se o usuário disser que não tem usuário de rede, o agente deve orientar para criar usuário primeiro (CREATE_USER)

Isso foi importante porque evita que o agente tente “criar VPN” como se fosse um processo de identidade.

CORPORATE_SYSTEMS

Você falou sobre sistemas internos (ERP, CRM, PROA):

Quando há erro de software específico, isso é CORPORATE_SYSTEMS

O agente deve coletar nome do sistema e mensagem de erro

Esse caso soou como “queremos separar falhas de sistema de falhas de infraestrutura”.

🧠 4. Regras de Inferência e Confirmação

Você detalhou várias regras importantíssimas:

Inferência

Você explicou que o agente pode fazer inferências leves:

Urgência → média se não houver palavras de impacto

Impacto → individual se não houver indicação de setor ou grupo

Requisição de equipamentos com “velho”, “novo”, “quero” pode ser inferida

Mas o agente não pode assumir:

Identificadores como patrimônio, IP, nome de usuário

Intenções ambíguas

Confirmação

Você deixou claro que:

Se o usuário corrige explicitamente (“digo, X”), isso deve sobrescrever

Se há conflito implícito, perguntar

Se um campo obrigatório não é preenchido após 3 tentativas, deve ocorrer handover (N2)

Essa regra foi consolidada para evitar loops de perguntas sem fim — algo que você inclusive identificou e diagnosticou como “amnésia de contexto”.

🔄 5. Workflow de Conversa e Multi-Turno

Você trouxe um aprendizado importante:

Problema:

O agente estava usando pinned_request apenas, ignorando respostas subsequentes. Isso causava loops — o agente perguntava, o usuário respondia, mas o agente continuava lendo só a requisição inicial e repetia a pergunta.

Solução:

Você definiu que:

O agente deve validar todas as mensagens trocadas, não apenas a primeira

O fluxo deve considerar o histórico de conversa

O extractor e o router devem usar o texto mais recente para extrair campos e reclassificar quando necessário

Esse insight foi repetido várias vezes e só veio depois de observar o comportamento em execução — algo que só um caso de uso real revela.
